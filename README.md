# ALTDA — ИИ-агент для образовательных программ АЦР

Oct 15, 2026 · @vladimir azanza @danjos91 @alexaappelgants

Хакатон, кейс №1 «Агенты и EdTech». Методист пишет запрос в свободной форме, а агент строит программу ДПП ПК или ДООП: компетенции (ЗУН), учебный план с точными часами, тесты, задания, планы занятий — и выгружает комплект в .docx.

## Быстрый старт

Нужен только Docker. Из корня репозитория:

```bash
cd deploy
docker compose up --build        # Java + Go; Java работает с нашим сервисом Go
docker compose down
```

Интерфейс: <http://localhost:8000/> (веб-интерфейс на русском, пять вкладок). Первая сборка долгая: Java компилируется внутри образа.

```bash
curl -s localhost:8000/health        # Java
curl -s localhost:8081/v1/health     # Go
./scripts/smoke_test.sh http://localhost:8000
```

- Java без Go (встроенная заглушка): `ALTDA_GO_CLIENT=mock docker compose up --build`.
- Подробности запуска: [`deploy/README.md`](deploy/README.md). Каждый сервис по отдельности: [`java-service/README.md`](java-service/README.md), [`go-service/README.md`](go-service/README.md).
- HTTP-контракт между сервисами: [`docs/API.md`](docs/API.md). Схема данных: [`schema/program.schema.json`](schema/program.schema.json).

### Ограничения текущей версии

- **Тексты шаблонные.** Каждый текст, который пишет генератор содержания, начинается с `[Шаблон]`, чтобы его было видно в программе и в .docx. Структура при этом корректна: часы сходятся, ключи тестов верны, у заданий есть критерии с баллами.
- **В отчёте всегда два предупреждения-ошибки `SECTION_MISSING`:** «Список источников» и «Нормативная база». Источники и нормативы берутся только из проверенного каталога, а каталога пока нет, поэтому ничего не выдумывается.
- **Профстандарты не выдумываются.** У компетенций ДПП ПК список связей с профстандартами пуст, хотя схема требует хотя бы одну связь.
- **Разбор запроса работает по правилам.** Он находит тип программы, часы, форму обучения и т. п., но не может определить область ИТ, аудиторию и входной уровень, поэтому всегда задаёт эти три вопроса.
- **Перегенерация по комментарию.** Шаблонный регенератор не понимает текст комментария: он возвращает модуль к шаблонной версии.

### Известные расхождения при интеграции

Найдены при чтении кода Java (на 17 октября); проверить и согласовать до 22-го:

- Кнопки «Перегенерировать» на вкладке «Содержание» всегда пересобирают всё содержание: Java вызывает `/v1/content` с `nodeIds: null`, хотя Go умеет работать по узлам.
- При утверждении варианта каркаса `SkeletonMaterializer` копирует в темы поля `kinds` и `practiceShareHint`, которых схема программы в теме не допускает.
- Интерфейс перерисовывает вкладку каждые 2 секунды, из-за чего введённый в поля ответов текст может пропадать.
- При утверждении каркаса `curriculum` строится заново из варианта, поэтому изменения, пришедшие из `skeleton/regenerate` в режиме программы, будут перезаписаны.

## Резюме и ключевые решения

В команде два бэкендера, поэтому работа делится на два равноценных сервиса. Java отвечает за сценарий, интерфейс и документы; Go — за движок: разбор запроса, каркас, содержание, распределение часов и проверку. С LLM будет общаться только Go.

1. **Один JSON как единый источник истины.** Весь комплект хранится в `program.json` по схеме `program.schema.json`. Файлы .docx, .pptx и тесты для LMS генерируются из него, поэтому никогда не противоречат друг другу.
2. **LLM не считает часы.** Модель предлагает модули, темы и относительные веса. Распределитель (сейчас в Go) переводит веса в часы с шагом 0,5, которые в сумме дают ровно запрошенный объём.
3. **Детерминированная проверка на Go.** Суммы часов, покрытие компетенций и битые ссылки проверяются кодом после каждого изменения. Когда появится LLM, исправлять он будет только те узлы, которые отметил валидатор.
4. **Ничего выдуманного.** Законы, приказы и профстандарты берутся из локального проверенного каталога. Всё остальное помечается в документе как «источник не подтверждён».
5. **Каждый шаг — отдельный компонент.** Разбор запроса, каркас, содержание и перегенерация реализованы за интерфейсами Go; шаблонные реализации заменяются реализациями с LLM без изменений остального кода.
6. **Обязательное утверждение человеком.** Содержание генерируется только после того, как методист утвердит цель, компетенции и часы.
7. **С LLM общается только Go.** Cloud.ru Foundation Models предоставляет API, совместимый с OpenAI ([evolution-openai](https://github.com/cloud-ru-tech/evolution-openai-python)). Go отвечает за параллельность (уже реализована с ограничением числа одновременных тем), повторные попытки и учёт токенов; Java никогда не обращается к модели напрямую.
8. **Содержание опирается на референсы (RAG)** *(не реализовано)*. Референсы методиста разбиваются на фрагменты и индексируются эмбеддингами Cloud.ru. Каждая тема получает ближайшие фрагменты, а тот же индекс помогает находить дословные заимствования.
9. **Прогресс в реальном времени.** Сейчас интерфейс опрашивает состояние раз в 2 секунды; SSE оставлен как возможное улучшение.

## Детерминированный распределитель часов

Часы считает код, а не LLM. Благодаря этому сумма точна и для 16, и для 500 часов, а каркас собирается за миллисекунды. Реализация: [`go-service/internal/service/allocator`](go-service/internal/service/allocator).

1. LLM возвращает модули и темы с относительным весом `weight` и видами работы темы (`kinds`): лекция, практика, лабораторная, самостоятельная.
2. Резервируются часы итоговой аттестации: 5 % объёма, не меньше 1 и не больше 8 часов, с шагом 0,5.
3. Остаток распределяется между модулями методом наибольшего остатка, затем тем же методом между темами внутри модуля.
4. Часы темы делятся на лекции, практику, лабораторные и самостоятельную работу в зависимости от форм работы темы, формы обучения и подсказки `practiceShareHint`.
5. Пересчитываются `contact`, `total` и `curriculum.totals`, а валидатор проверяет их ещё раз.

Метод наибольшего остатка для H часов и весов w сначала округляет вниз, затем раздаёт r оставшихся часов элементам с наибольшими дробными остатками:

![Формула метода наибольшего остатка](docs/img/plan.png)

Здесь δ равно 1 для r элементов с наибольшей дробной частью и 0 для остальных.

Часы кратны 0,5: формула применяется к полуакадемическим часам, то есть вместо H берётся 2H, а результат делится на 2. Так суммы остаются точными, а короткие темы получают, например, 1,5 часа практики.

- **Минимум 1 час на тему.** Если часов не хватает, например 20 тем в интенсиве на 16 часов, распределитель возвращает ошибку, а каркас отбрасывает такой вариант. Когда появится LLM, он будет просить объединить темы.
- **Заблокированные узлы.** Тема с `_meta.locked` сохраняет свои часы, остальные делят то, что осталось. Если все темы заблокированы и сумма не сходится, это ошибка.
- **Минимальная доля практики.** Если запрос требует её, распределитель переносит по полчаса из лекций в практику, пока доля не будет достигнута; если это невозможно, пишет предупреждение.
- **Пропорции — в конфигурации** (`allocator.DefaultConfig()`): доля практики по умолчанию 60 % (30 % во вводных модулях), доля самостоятельной работы 10 % для очной, 25 % для очно-заочной и 50 % для заочной формы. Значения предварительные: PM должен откалибровать их по примерам АЦР.
- **Автоматические тесты.** Для случайных объёмов от 16 до 500 часов, весов и составов тем сумма должна быть ровно H, а все формулы — выполняться на каждом уровне.

## Проверка, источники и профстандарты

Валидатор работает в сервисе Go и за миллисекунды проверяет программу после каждого изменения; его результаты составляют отчёт автопроверки, который требует кейс. Правила и их коды совпадают с эталоном `tools/validate_reference.py`; на примере `schema/example_program.json` результат тот же, что у эталона (одно предупреждение `SOURCE_UNVERIFIED`).

| Код | Что проверяет | Уровень |
| --- | --- | --- |
| `HOURS_CONTACT`, `HOURS_ROW_SUM` | Каждая строка: контактная работа = лекции + практика + лабораторные; всего = контактная + самостоятельная + аттестация | ошибка |
| `HOURS_TOPICS_EQ_MODULE` | Сумма тем совпадает с модулем | ошибка |
| `HOURS_TOTALS_FIELD`, `HOURS_EQ_REQUESTED` | Итоги сходятся, и план в сумме даёт ровно запрошенные часы | ошибка |
| `HOURS_PRACTICE_SHARE` | Доля практики не меньше заявленной в запросе | ошибка |
| `HOURS_ACTIVITIES_EQ_TOPIC` | Активности темы повторяют её часы по видам работы | ошибка |
| `LECTURE_MINUTES` | Минуты планов лекций темы = лекционные часы × 45 | ошибка |
| `TASK_MAXSCORE`, `TASK_DURATION` | Баллы критериев сходятся; задания темы укладываются в её часы практики и лабораторных | ошибка |
| `CALENDAR_SESSION_NUMBERS` | Занятия пронумерованы подряд с 1 | ошибка |
| `CALENDAR_HOURS` | Занятия в сумме дают всего минус самостоятельная работа | предупреждение |
| `COVERAGE_OUTCOME_TAUGHT` | Каждый результат ЗУН есть хотя бы в одной теме | ошибка |
| `COVERAGE_OUTCOME_ASSESSED` | Каждый результат ЗУН проверяется не менее чем двумя средствами | ошибка |
| `CONSISTENCY_DANGLING_OUTCOME`, `_TOPIC`, `_REFERENCE`, `_SOURCE` | Ни один ID не ссылается на несуществующий результат, тему, референс или источник | ошибка |
| `CONSISTENCY_OUTCOME_PREFIX`, `CONSISTENCY_PROFSTANDARD_LINK` | Результаты начинаются с ID своей компетенции; связи с профстандартами ведут в `dpp.profStandards` | ошибка |
| `ORDER_PREREQUISITES` | Пререквизиты темы стоят раньше неё | ошибка |
| `TEST_KEY` | Ключ каждого вопроса корректен для его типа | ошибка |
| `SKELETON_MODULE_WEIGHTS`, `SKELETON_TOPIC_WEIGHTS`, `SKELETON_DANGLING_OUTCOME` | Проверки варианта каркаса до распределения часов | ошибка |
| `SOURCE_UNVERIFIED` | Источник не подтверждён | предупреждение |
| `SECTION_MISSING` | Раздел шаблона не заполнен | ошибка |
| `TOOL_OUTDATED` | У изучаемого инструмента есть более новая версия (для актуализации программ) | предупреждение |
| `COPY_OVERLAP` *(не реализовано)* | Сгенерированный текст слишком похож на референс: близость эмбеддингов и совпадение последовательностей из 8 слов | предупреждение |

**Политика источников**

- **Нормативная база и профстандарты:** только из локального каталога `catalog/*.json`, собранного вручную по официальным реестрам. Если LLM предлагает код, которого нет в каталоге, он получает статус `unverified`. *Каталога пока нет.*
- **Книги и статьи:** LLM их предлагает, а верификатор проверяет ISBN, DOI или доступность URL. Иначе статус `unverified`, и в .docx печатается «[источник не подтверждён]».
- **Официальная документация инструментов:** предпочтительнее книг, потому что её URL легко проверить.
- **Референсы методиста:** помечаются как `user_provided`.

**Цикл исправления** *(зависит от LLM, не реализован)*: ошибки передаются навыку `repair` только с проблемными узлами, и проверка запускается снова, максимум 2 раза. Всё, что осталось, попадает в отчёт для методиста.

## Точечная доработка и каскадная перегенерация

У каждого узла есть стабильный ID: модуль `M2`, тема `T2.3`, результат `C1.K1`, лекция `L2.3`, задание `ST203`, тест `TEST2`, вопрос `Q-M2-T3-1`. Эти ID назначает сервис, а не генератор, поэтому модель не может их нарушить. Правка пересобирает только затронутое.

- **`POST /v1/content` с `nodeIds`:** пересобирает только указанные узлы и всё, что от них зависит. Можно указать модуль, тему, результат, лекцию, задание, тест, вопрос или `assessment` (все вопросы и задания). Пустой список — вся программа.
- **Блокировка:** узлы с `_meta.locked: true`, то есть отредактированные человеком, не трогаются. Для `content` они пропускаются, для `skeleton/regenerate` явный запрос заблокированного узла даёт 409 `node_locked`.
- **Пересчёт часов после ручной правки:** `POST /v1/allocate` сохраняет заблокированное и пересчитывает остальное. Содержание тем, чьи часы изменились, устаревает: валидатор это показывает, и его нужно пересобрать через `content` с `nodeIds`.
- **Что вернётся:** `content` возвращает программу и `issues` (результат валидатора), `skeleton/regenerate` — программу и `changedPaths` либо новые варианты.
- **Календарь и разделы шаблона** пересчитываются при каждой генерации: это производные данные, а не содержание.
- **Граф — в Java, выполнение — в Go:** Java решает, какие узлы пересобирать, и передаёт их в `nodeIds`; Go генерирует темы параллельно с ограничением числа одновременных.

## Расширенный объём *(не начато)*

С двумя сеньорами команда может сделать оба пункта «сверх плана» в дополнение к «желательным». Их начинают, только если обязательная часть проходит все 5 чек-листов.

| Функция | Как работает | Ответственный |
| --- | --- | --- |
| RAG по референсам | Java разбивает референсы на фрагменты; Go считает эмбеддинги и ищет ближайшие. При генерации темы подтягиваются ближайшие фрагменты, а тема сохраняет свои `referenceIds` | Go |
| Контроль заимствований | Тот же индекс сравнивает каждый сгенерированный текст с референсами; при сильном сходстве — предупреждение `COPY_OVERLAP` | Go |
| Актуализация старой программы | Старый .docx импортируется в схему; Go проверяет версии `tools` на официальных страницах; навык `actualize` переписывает только темы с пометкой `TOOL_OUTDATED`. Результат получает `lineage.operation = actualize` | Go + Java |
| Адаптация под другую аудиторию | Структура и часы сохраняются; перегенерируются цель, формулировки результатов и примеры. `lineage.operation = adapt_audience` | Java |
| Адаптация под другой объём | Распределитель пересчитывает часы без LLM, перегенерируются только темы, чьи часы сильно изменились. `lineage.operation = adapt_hours` | Java |

Поле `lineage` и список `changes_summary` показывают методисту, из какой программы получена новая и что изменилось.

## Стек и распределение ролей

Каждый сеньор владеет целым сервисом одинакового веса. Python и PM отвечают за качество содержания и оценку, где нужно немного кода.

| Участник | Отвечает за | Технологии |
| --- | --- | --- |
| Backend Java | Сервис Java: единый API, оркестратор и состояния, веб-интерфейс, выгрузка .docx, контроль версий и блокировок; далее — выгрузка .pptx, приём референсов, адаптации | Spring Boot 3, виртуальные потоки, Apache POI, хранение в памяти, JavaScript без фреймворков |
| Go | Сервис Go: разбор запроса, каркас, содержание, распределитель часов, валидатор; далее — LLM-шлюз (параллельность и контроль стоимости), эмбеддинги и RAG, проверка источников и версий, выгрузка в LMS, развёртывание в Cloud.ru | Go, стандартная библиотека (`net/http`, `log/slog`), без внешних зависимостей; далее — клиент, совместимый с OpenAI |
| Python (начальный уровень) | Промпты на русском с few-shot примерами, каталог нормативной базы и профстандартов, сравнение моделей, набор для оценки | Jupyter-ноутбук и библиотека `evolution-openai` |
| PM | Карта двух шаблонов АЦР по разделам и `json_path`, чек-листы как тестовые сценарии, тестирование в роли методиста, расчёт эффекта, сценарий демо и питч | Документы и таблицы |

- **Контракт Java ↔ Go:** синхронные HTTP-маршруты `/v1/...` с `schemaVersion` в каждом теле и ошибками `{error, message}` (`bad_request`, `node_locked`, `llm_timeout`, `llm_error`, `schema_invalid`). Подробно: [`docs/API.md`](docs/API.md). Java показывает ошибки Go как типизированные ответы интерфейсу.
- **Почему движок на Go:** ему естественно генерировать десятки тем одновременно с ограничением числа запросов к Cloud.ru. Java остаётся то, что она делает лучше всего: предметная логика и документы Office.
- **Почему документы на Java:** библиотеки для Word и PowerPoint в Java зрелые и бесплатные.
- **Интерфейс:** одностраничное приложение на JavaScript; состояние опрашивается раз в 2 секунды. Вкладки: заявка и уточнения; каркас с вариантами; содержание; проверка и отчёт; выгрузка.
- **Контракт данных:** `program.schema.json`. Он версионируется. Go читает программу так, что поля, которых он не знает, проходят без изменений, поэтому сервисы можно развивать независимо.
- **Шаблоны и промпты:** `prompts/PROMPTS.md` — промпты агентного пайплайна. Для дополнительных функций добавятся `actualize` и `adapt`.

Разработка идёт до **23 октября**; сквозная интеграция Java + Go — **22 октября**, затем тесты каждый день. План на 10 дней сокращён: дополнительные функции начинаются, только если проходит основная демонстрация.

## Риски, демо и метрики

Главный риск при двух сервисах — что они не стыкуются; поэтому контракт зафиксирован в [`docs/API.md`](docs/API.md), у Java есть заглушка Go, а сквозной тест выполняется ежедневно. Лимит в 20 минут на программу в 72 часа нужно измерить, как только подключится LLM.

| Риск | Меры |
| --- | --- |
| Java и Go не стыкуются | Контракт и JSON-схема зафиксированы; у Java заглушка Go; ежедневный сквозной тест; список известных расхождений выше |
| Нет доступа к Cloud.ru FM | Шаблонные реализации сохраняют работоспособность всего потока; уточнить доступ, ключ API и выход в интернет с ВМ |
| Комплект на 72 часа собирается дольше 20 минут | Go генерирует темы параллельно с ограничением числа запросов; быстрая модель для содержания и сильная для каркаса; замеры после подключения LLM |
| Каркас собирается дольше 3 минут | Один вызов LLM плюс распределитель, который работает за миллисекунды |
| Модель возвращает некорректный JSON | Структурированный вывод, если модель его поддерживает; проверка и повтор с текстом ошибки, не более 2 раз; вариант, не прошедший проверку, отбрасывается |
| Выдуманные профстандарты или источники | Только локальный каталог; всё остальное помечается как неподтверждённое |
| Сложный шаблон АЦР | PM размечает его разделы; выгрузка строится по этой карте на реальном примере |
| Дополнительные функции отнимают время у обязательных | Начинаются, только если проходят чек-листы |
| Низкое качество русского текста | Сравнить 2–3 модели на одном промпте |

**Сценарий демо (5–7 минут)**

1. Новый запрос в живом режиме → каркас с «зелёной» таблицей часов меньше чем за 3 минуты.
2. Изменить час вручную → валидатор сразу показывает ошибку *(редактор часов в интерфейсе пока в планах)*.
3. Утвердить → показать полный комплект (сгенерированный заранее, если не хватает времени) с отчётом проверки.
4. «Замени тему 2.3» → меняются только зависимые узлы.
5. Скачать .docx *(.pptx и GIFT — в планах)*.

**Метрики для защиты**, на основе `generation`:

- **Стоимость:** входные и выходные токены по каждому шагу × тариф Cloud.ru = рубли на программу *(считаются после подключения LLM)*.
- **Время методиста:** сегодня от 2 до 8 недель на программу (данные кейса) против часов на проверку, замеренных в тестах PM.
- **Качество:** доля пунктов 5 чек-листов, выполненных без вмешательства.
