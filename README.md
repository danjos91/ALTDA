## Quick test (Java service)

Java orchestration service lives in `java-service/` (port **8000**). Default `altda.go.client=mock` — no Go service required.

```bash
# start (mock Go client)
cd java-service && ./run.sh
# or: ./mvnw spring-boot:run
# or: docker build -t altda-java . && docker run --rm -p 8000:8000 altda-java

# smoke (in another terminal, from repo root)
./scripts/smoke_test.sh http://localhost:8000
```

One-shot generate (auto-approval, for automated tests):

```bash
curl -sS -X POST http://localhost:8000/api/generate \
  -H 'Content-Type: application/json' \
  -d '{"request":"ДПП ПК Анализ данных на Python, 72 ч","answers":{"entryLevel":"Базовый"}}'
```

Health: `GET http://localhost:8000/health`. UI: open `http://localhost:8000/` (vanilla SPA, Russian). Unit tests: `cd java-service && ./mvnw test`. Manual UI checklist: [`java-service/README.md`](java-service/README.md). HTTP contract with Go: [`docs/API.md`](docs/API.md).

## Резюме и ключевые решения

В команде два бэкендера, поэтому работа делится на два равноценных сервиса. Java отвечает за сценарий, предметную логику и документы; Go — за движок, который выполняет навыки через Cloud.ru, за проверку и верификацию источников. Так обязательные требования готовы к 7-му дню, а дни 8 и 9 остаются на дополнительные функции.

1. **Один JSON как единый источник истины.** Весь комплект хранится в `program.json` по схеме `program.schema.json`. Файлы .docx, .pptx и тесты для LMS генерируются из него, поэтому никогда не противоречат друг другу.
2. **LLM не считает часы.** Модель предлагает модули, темы и относительные веса. Распределитель на Java переводит веса в целые часы, которые в сумме дают ровно запрошенный объём.
3. **Детерминированная проверка на Go.** Суммы часов, покрытие компетенций и битые ссылки проверяются кодом после каждого изменения. LLM исправляет только те узлы, которые отметил валидатор.
4. **Ничего выдуманного.** Законы, приказы и профстандарты берутся из локального проверенного каталога. Всё остальное помечается в документе как «источник не подтверждён».
5. **Каждый шаг — отдельный навык.** Навык — это файл .md на русском языке и JSON-схема его ответа. Их выполняет сервис Go, поэтому логику можно почти без изменений перенести в GigaCowork.
6. **Обязательное утверждение человеком.** Содержание генерируется только после того, как методист утвердит цель, компетенции и часы.
7. **С LLM общается только Go.** Cloud.ru Foundation Models предоставляет API, совместимый с OpenAI ([evolution-openai](https://github.com/cloud-ru-tech/evolution-openai-python)). Go отвечает за параллельность, повторные попытки и учёт токенов; Java никогда не обращается к модели напрямую.
8. **Содержание опирается на референсы (RAG).** Референсы методиста разбиваются на фрагменты и индексируются эмбеддингами Cloud.ru в pgvector. Каждая тема получает ближайшие фрагменты, а тот же индекс помогает находить дословные заимствования.
9. **Прогресс в реальном времени.** Интерфейс получает по SSE каждую часть каркаса и комплекта сразу по готовности — это хорошо смотрится на демо.

## Детерминированный распределитель часов

Часы считает Java, а не LLM. Благодаря этому сумма точна и для 16, и для 500 часов, а каркас собирается за секунды.

1. LLM возвращает модули и темы с относительным весом `weight` и профилем темы: теоретическая, практическая или лабораторная.
2. Резервируются часы итоговой аттестации по шаблону. Значение настраивается и берётся из примеров АЦР.
3. Остаток распределяется между модулями методом наибольшего остатка, затем тем же методом между темами внутри модуля.
4. Часы темы делятся на лекции, практику, лабораторные и самостоятельную работу в зависимости от формы обучения и профиля темы.
5. Пересчитываются `contact`, `total` и `curriculum.totals`, а валидатор проверяет их ещё раз.

Метод наибольшего остатка для H часов и весов w сначала округляет вниз, затем раздаёт r оставшихся часов элементам с наибольшими дробными остатками:

![Формула метода наибольшего остатка](docs/img/plan.png)

Здесь δ равно 1 для r элементов с наибольшей дробной частью и 0 для остальных.

Часы кратны 0,5: формула применяется к полуакадемическим часам, то есть вместо H берётся 2H, а результат делится на 2. Так суммы остаются точными, а короткие темы получают, например, 1,5 часа практики.

- **Минимум 1 час на тему.** Если часов не хватает, например 20 тем в интенсиве на 16 часов, распределитель просит LLM объединить темы. Предел числа тем на час калибруется по двум примерам АЦР.
- **Пропорции по формам обучения — в конфигурации.** Доля практики для очной и заочной форм хранится в файле, а не в коде. PM берёт эти значения из примеров АЦР.
- **Автоматический тест.** Для любого H от 16 до 500 и случайных весов сумма должна быть ровно H. Это несколько строк свойств-ориентированного теста на JUnit.

## Проверка, источники и профстандарты

Валидатор работает в сервисе Go и за миллисекунды проверяет комплект после каждого изменения; его результаты составляют отчёт автопроверки, который требует кейс. Все правила, кроме COPY\_OVERLAP, уже реализованы в `validate_reference.py` как спецификация для переноса на Go.

| Код | Что проверяет | Уровень |
| --- | --- | --- |
| HOURS\_CONTACT, HOURS\_ROW\_SUM | Каждая строка: контактная работа = лекции + практика + лабораторные; всего = контактная + самостоятельная + аттестация | ошибка |
| HOURS\_TOPICS\_EQ\_MODULE | Сумма тем совпадает с модулем | ошибка |
| HOURS\_TOTALS\_FIELD, HOURS\_EQ\_REQUESTED | Итоги сходятся, и план в сумме даёт ровно запрошенные часы | ошибка |
| COVERAGE\_OUTCOME\_TAUGHT | Каждый результат ЗУН есть хотя бы в одной теме | ошибка |
| COVERAGE\_OUTCOME\_ASSESSED | Каждый результат ЗУН проверяется вопросом или критерием | ошибка |
| CONSISTENCY\_DANGLING\_OUTCOME, \_TOPIC, \_REFERENCE | Ни один ID не ссылается на несуществующий результат, тему или референс | ошибка |
| TEST\_KEY | В каждом вопросе с одним выбором ровно один правильный ответ | ошибка |
| SOURCE\_UNVERIFIED | Источник не подтверждён | предупреждение |
| SECTION\_MISSING | Раздел шаблона не заполнен | ошибка |
| TOOL\_OUTDATED | У изучаемого инструмента есть более новая версия (для актуализации программ) | предупреждение |
| COPY\_OVERLAP | Сгенерированный текст слишком похож на референс: близость эмбеддингов и совпадение последовательностей из 8 слов | предупреждение |

**Политика источников**

- **Нормативная база и профстандарты:** только из локального каталога `catalog/*.json`, собранного вручную по официальным реестрам. Если LLM предлагает код, которого нет в каталоге, он получает статус `unverified`.
- **Книги и статьи:** LLM их предлагает, а верификатор проверяет ISBN, DOI или доступность URL. Иначе статус `unverified`, и в .docx печатается «\[источник не подтверждён\]».
- **Официальная документация инструментов:** предпочтительнее книг, потому что её URL легко проверить.
- **Референсы методиста:** помечаются как `user_provided`.

**Цикл исправления:** ошибки передаются навыку `repair` только с проблемными узлами, и проверка запускается снова, максимум 2 раза. Всё, что осталось, попадает в отчёт для методиста.

## Точечная доработка и каскадная перегенерация

У каждого узла есть стабильный ID и список зависящих от него узлов. Поэтому правка пересобирает только затронутое. Цепочка зависимостей: результат ЗУН → тема → лекция, семинары и вопросы по этой теме.

Пример: «замени тему 2.3».

1. Навык `edit_node` переписывает T2.3 (название, содержание и `outcomeIds`) и сохраняет её часы.
2. Инвалидируются L2.3, S2.3.\* и вопросы с `topic_id: T2.3`.
3. Перегенерируются только эти узлы. Узлы с `locked: true`, то есть отредактированные человеком, не трогаются.
4. Валидатор проверяет всю программу, а разница показывается в `changed_paths`.

- **«Усложни тест»:** перегенерируется только банк вопросов модуля с более высоким `difficulty`.
- **Граф — в Java, выполнение — в Go:** Java вычисляет, какие узлы инвалидировать, и параллельно запрашивает у Go по одному навыку на узел.

## Расширенный объём (дни 8 и 9)

С двумя сеньорами команда может сделать оба пункта «сверх плана» в дополнение к «желательным». Их начинают, только если к 7-му дню обязательная часть проходит все 5 чек-листов.

| Функция | Как работает | Ответственный |
| --- | --- | --- |
| RAG по референсам | Java разбивает референсы на фрагменты; Go считает эмбеддинги и сохраняет их в pgvector. При генерации темы подтягиваются ближайшие фрагменты, а тема сохраняет свои `reference_ids` | Go |
| Контроль заимствований | Тот же индекс сравнивает каждый сгенерированный текст с референсами; при сильном сходстве — предупреждение COPY\_OVERLAP | Go |
| Актуализация старой программы | Старый .docx импортируется в схему; Go проверяет версии `tools` на официальных страницах; навык `actualize` переписывает только темы с пометкой TOOL\_OUTDATED. Результат получает `lineage.operation = actualize` | Go + Java |
| Адаптация под другую аудиторию | Структура и часы сохраняются; перегенерируются цель, формулировки результатов и примеры. `lineage.operation = adapt_audience` | Java |
| Адаптация под другой объём | Распределитель пересчитывает часы без LLM, перегенерируются только темы, чьи часы сильно изменились. `lineage.operation = adapt_hours` | Java |

Поле `lineage` и список `changes_summary` показывают методисту, из какой программы получена новая и что изменилось.

## Стек и распределение ролей

Каждый сеньор владеет целым сервисом одинакового веса. Python и PM отвечают за качество содержания и оценку, где нужно немного кода.

| Участник | Отвечает за | Технологии |
| --- | --- | --- |
| Backend Java&#32; | Сервис Java: единый API с SSE, оркестратор и граф зависимостей, распределитель часов, приём и разбиение референсов, выгрузка .docx и .pptx, веб-интерфейс, адаптации | Spring Boot, виртуальные потоки, Apache Tika, poi-tl и Apache POI, PostgreSQL, Thymeleaf + htmx |
| Go | Сервис Go: исполнитель навыков, LLM-шлюз с параллельностью и контролем стоимости, эмбеддинги и RAG, валидатор, проверка источников и версий, выгрузка в LMS, развёртывание в Cloud.ru, актуализация программ | Go, клиент, совместимый с OpenAI, pgvector, JSON Schema |
| Python (начальный уровень) | Навыки (промпты на русском) с few-shot примерами, каталог нормативной базы и профстандартов, сравнение моделей, набор для оценки | Jupyter-ноутбук и библиотека `evolution-openai` |
| PM | Карта двух шаблонов АЦР по разделам и `json_path`, чек-листы как тестовые сценарии, тестирование в роли методиста, расчёт эффекта, сценарий демо и питч | Документы и таблицы |

- **Контракт Java ↔ Go фиксируется в OpenAPI в 1-й день:** `POST /skills/{name}/run` принимает программу, ID узлов для генерации и параметры, а возвращает JSON-патч и расход токенов. Go проверяет ответ по схеме навыка, прежде чем его вернуть. Также: `POST /validate`, `POST /verify` и `POST /export/lms`. Каждый сервис стартует с заглушкой другого.
- **Почему движок на Go:** ему естественно генерировать десятки модулей одновременно с ограничением числа запросов к Cloud.ru. Java остаётся то, что она делает лучше всего: предметная логика и документы Office.
- **Почему документы на Java:** для Word-шаблона АЦР poi-tl позволяет ставить метки `{{...}}` и циклы по строкам таблиц прямо в копию оригинального .docx.
- **Интерфейс:** Thymeleaf + htmx позволяет обойтись без SPA и остаться в стеке Java; прогресс приходит по SSE. Экраны: чат с вложениями; редактируемая таблица часов с живыми суммами и кнопкой «Утвердить»; комплект с отчётом проверки и кнопками «Переделать»; скачивание.
- **Контракт данных:** `program.schema.json`. Он версионируется, и оба сервиса проходят контрактные тесты на одном и том же примере.
- **Навыки:** по одному файлу на навык (`classify_request`, `ask_clarifications`, `build_skeleton`, `generate_module`, `generate_tests`, `repair`, `edit_node`). Для дополнительных функций добавляются `actualize` и `adapt`. В каждом файле — инструкция, входные данные, схема ответа и пример.

## Риски, демо и метрики

При двух сервисах главный новый риск — что они не стыкуются; поэтому контракт фиксируется в 1-й день, а сквозной тест идёт каждый день начиная с 3-го. Лимит в 20 минут на программу в 72 часа измеряется с 4-го дня.

| Риск | Меры |
| --- | --- |
| Java и Go не стыкуются | Контракт OpenAPI и JSON-схема фиксируются в 1-й день; у каждого сервиса заглушка другого; ежедневный сквозной тест с 3-го дня |
| Комплект на 72 часа собирается дольше 20 минут | Go генерирует модули параллельно с ограничением числа запросов; быстрая модель для содержания и сильная для каркаса; замеры с 4-го дня |
| Каркас собирается дольше 3 минут | Один вызов LLM плюс распределитель; SSE показывает каждую часть сразу по готовности |
| Модель возвращает некорректный JSON | Структурированный вывод, если модель его поддерживает (проверить в 1-й день); проверка и повтор с текстом ошибки, не более 2 раз |
| Выдуманные профстандарты или источники | Только локальный каталог; всё остальное помечается как неподтверждённое |
| Сложный шаблон АЦР | PM размечает его разделы в дни 1–3; выгрузка строится по этой карте на реальном примере |
| Дополнительные функции отнимают время у обязательных | Начинаются, только если к 7-му дню обязательная часть проходит 5 чек-листов |
| Низкое качество русского текста | Сравнить 2–3 модели на одном промпте в первые дни |

**Сценарий демо (5–7 минут)**

1. Новый запрос в живом режиме → каркас с «зелёной» таблицей часов меньше чем за 3 минуты.
2. Изменить час вручную → валидатор сразу показывает ошибку.
3. Утвердить → показать полный комплект (сгенерированный заранее, если не хватает времени) с отчётом проверки.
4. «Замени тему 2.3» → меняются только зависимые узлы.
5. Скачать .docx, .pptx и GIFT.

**Метрики для защиты**, на основе `generation`:

- **Стоимость:** входные и выходные токены по каждому навыку × тариф Cloud.ru = рубли на программу.
- **Время методиста:** сегодня от 2 до 8 недель на программу (данные кейса) против часов на проверку, замеренных в тестах PM.
- **Качество:** доля пунктов 5 чек-листов, выполненных без вмешательства.
