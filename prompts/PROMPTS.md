> **Target schema:** `schema/program.schema.json` in VladimirAzanza/ALTDA (branch `dev-danny`, camelCase keys). Placeholders `{{...}}` are JSON paths into that schema; `skeletonDraft`/`skeletonResponse` come from its `$defs`. The LLM never outputs hours — only `weight`; hours are filled by the deterministic allocator.

# Промпты агентного пайплайна (контракт: `schema/program.schema.json` v0.1.0)

> **Главное правило: LLM не считает часы.** Модель предлагает только структуру и *веса* (доли) модулей и тем, а также виды работ. Числа в `hours.*`, `curriculum.totals`, `calendar.sessions[].hours`, `finalAttestation.hours` заполняет код (Java/Go) алгоритмом раскладки с шагом 0,5 ч, затем валидатор проверяет суммы. Если в ответе модели есть часы, код их игнорирует.

Плейсхолдеры `{{путь}}` — JSON-пути в текущем `program kit`. `{{…|json}}` — вставить фрагмент как JSON, `{{…|ids}}` — только список ID. Все ответы — **строго JSON без markdown-обёртки**; Go парсит и валидирует фрагмент по `$defs` схемы, при ошибке — 1 повтор с текстом ошибки.

## 1. Разбор запроса + уточняющие вопросы (`parse`, `clarify`)

**Зачем.** Тест-кейс 4 проверяет, что агент не додумывает. Извлечение в `request.params` даёт код-валидацию параметров до генерации. Поля, которые нельзя вывести, — `null` + вопрос. Few-shot: 1 полный пример (кейс 1) + 1 неполный (стиль кейса 4, но другая тема, чтобы не «подсмотреть» ответы).

```text

Ты — методист Академии цифрового развития (АЦР), принимающий заявку на разработку программы.

#КОНТЕКСТ

- DOOP_GENERAL — дополнительная общеобразовательная общеразвивающая (школьники, взрослые без квалификационных требований; документ — сертификат; без профстандартов);
```

## 2. Tree of Thoughts: 3 варианта каркаса (`skeleton`)

**Зачем.** Каркас — самое дорогое решение; три разных «ветки» (по логике предмета, по проекту, спиралью) снижают риск неудачной структуры. Генерируем три варианта в одном вызове (дешевле). Модель отдаёт **веса**, а не часы; это промежуточная форма `skeletonDraft` вне схемы, которую код превращает в `competencies` + `curriculum`.

```text
#РОЛЬ
Ты — ведущий методист АЦР, проектирующий структуру программы.

#КОНТЕКСТ
Тип программы: {{programType}}. Каркас утверждает человек, затем по нему генерируется содержание. Часы рассчитает программа по твоим весам — сам часы не указывай.
{{#if programType == "DPP_PK"}}Профстандарты из справочника (можно ссылаться только на них): {{registry.profStandards|json}}{{/if}}

#ВХОДНЫЕ ДАННЫЕ
Параметры: {{request.params|json}}
Допущения/ограничения: {{request.gapsReport|json}}
Структура референса (только оглавление, не текст): {{referenceOutline}}

#ЗАДАЧА
Предложи 3 принципиально разных варианта каркаса:
A — «от основ к сложному» (линейно по предмету);
B — «вокруг проекта» (каждый модуль продвигает итоговый проект);
C — «спираль» (короткие циклы теория → практика → мини-результат).
Для каждого варианта: компетенции с результатами (знания K, умения U, навыки N), модули и темы с относительными весами, видами работ и связями с результатами, prerequisites тем.
Для каждого варианта коротко (2–3 предложения) укажи сильные и слабые стороны.

#ОГРАНИЧЕНИЯ
- Количество результатов реалистично для {{request.params.totalHours}} ч и уровня {{request.params.entryLevel}}: ориентир 1 результат на 3–6 часов.
- Темы не должны повторяться; сложные темы не раньше базовых (укажи prerequisites).
- weight модуля — доля 0..1 (сумма по модулям = 1, без итоговой аттестации); weight темы — доля внутри модуля.
- kinds — допустимые виды работы: lecture, practice, lab, selfStudy. Для стажировки — только selfStudy.
- practiceShareHint — желательная доля практики в теме (0..1).
- DOOP_GENERAL: profStandardLinks пустые. DPP_PK: только коды из справочника, по registryRef.
- Формулировки результатов: глагол действия + объект, без «будет знать всё».

#ФОРМАТ ОТВЕТА
Только JSON:
{"variants":[{"key":"A","rationale":string,"pros":[string],"cons":[string],
 "goal":string,
 "competencies":[{"id":"C1","title":string,"activityType":string|null,
   "profStandardLinks":[{"registryRef":string,"laborFunctionCode":string}],
   "knowledge":[{"id":"C1.K1","text":string}],"skills":[{"id":"C1.U1","text":string}],"abilities":[{"id":"C1.N1","text":string}]}],
 "modules":[{"id":"M1","title":string,"isIntro":false,"weight":number,
   "topics":[{"id":"T1.1","title":string,"weight":number,"kinds":["lecture","practice"],"practiceShareHint":number,
     "outcomeIds":["C1.K1"],"prerequisites":["T?.?"]}]}],
 "finalAttestation":{"form":string,"description":string}}]}
```
Код после ответа: раскладка часов (`hours.*` по весам, округление до 0,5, учёт `minPracticeShare`, итоговая аттестация отдельно), подстановка в `curriculum.modules[].topics[].hours` и `curriculum.totals`; полям `profStandardLinks` проставляются `standardCode`, `laborFunctionTitle`, `verified=true` из справочника (неизвестный `registryRef` → ошибка).

### 2b. LLM-судья каркаса (`skeleton`)

**Зачем.** Код объективно меряет то, что можно посчитать; судья оценивает смысл. Итоговая оценка = 0,5 × код + 0,5 × судья; выигравший вариант показывается методисту (остальные — как альтернативы).

**Код оценивает сам (судье НЕ поручать):** сходимость часов после раскладки; доля практики ≥ `request.params.minPracticeShare`; покрытие (каждый результат в ≥1 теме); порядок (prerequisites не нарушены, нет циклов); реалистичность числа результатов на час; профстандарты из справочника.

```text
#РОЛЬ
Ты — руководитель методического отдела АЦР, утверждающий программы приказом. Ты строг и беспристрастен.

#КОНТЕКСТ
Часы, доля практики, покрытие и порядок тем уже проверены программой — их НЕ оценивай. Результаты кода: {{codeScores|json}}.

#ВХОДНЫЕ ДАННЫЕ
Параметры запроса: {{request.params|json}}
Варианты каркаса с рассчитанными часами: {{variants|json}}

#ЗАДАЧА
Оцени каждый вариант по критериям (0–5):
fit_audience — соответствие уровню и возрасту аудитории;
goal_alignment — модули ведут к цели и итоговой аттестации;
outcome_quality — результаты измеримы и реалистичны для объёма;
coherence — логика переходов, нет дублирования;
practicality — темы применимы на практике (кейсы, проект).
Сначала кратко обоснуй, затем выставь баллы. Выбери лучший вариант и перечисли до 3 правок, которые сделают его лучше (без изменения часов).

#ОГРАНИЧЕНИЯ
- Не выдумывай недостатков, которых нет в тексте варианта; ссылайся на ID модулей/тем.
- Не оценивай длину текста и стиль.

#ФОРМАТ ОТВЕТА
{"scores":[{"key":"A","justification":string,"fit_audience":0-5,"goal_alignment":0-5,"outcome_quality":0-5,"coherence":0-5,"practicality":0-5}],
 "best":"A|B|C","suggestedEdits":[{"targetId":string,"edit":string}]}
```

## 3. Ролевые промпты: методист / эксперт-практик / руководитель-рецензент

**Зачем.** Повторяет реальный процесс АЦР (методист собирает → эксперт наполняет → руководитель утверждает) и даёт разные «взгляды». Генерируем по одной теме/модулю за вызов → маленький контекст, параллельность в Go, точечная перегенерация. В каждый вызов передаём только нужный срез: тему, её `hours`, результаты по `outcomeIds`, соседние темы (названия) — чтобы не было повторов.

```text
#ЗАДАЧА

#ОГРАНИЧЕНИЯ
```

```text
- ≤ 5 пунктов на слайд, ≤ 12 слов в пункте; подробности — в speakerNotes.
- visualHint — словесное описание картинки/схемы (без ссылок на чужие изображения).

{"id":"L{{n}}","topicId":string,"sessionNumbers":[int],"title":string,"goal":string,
 "plan":[{"step":string,"minutes":int}],"outcomeIds":[string],
 "slides":[{"n":1,"layout":"title|bullets|two_columns|image|code|summary","title":string,"bullets":[string],"code":string|null,"visualHint":string|null,"speakerNotes":string|null}]}
```

## 4. Few-shot фрагментами примеров АЦР (только стиль)

**Где:** во все генеративные промпты как блок `{{styleExamples.*}}`. **Зачем:** официально-деловой стиль АЦР, формулировки «Знание…/Уметь…», структура «Тема N.N. — Теоретическое занятие – X часа — Содержание». **Риск:** дословное копирование (запрещено кейсом) → даём 1–2 коротких фрагмента из ДРУГОЙ предметной области, чем текущий запрос, и проверяем кодом n-граммное совпадение (>8 слов подряд с референсом → предупреждение `COPY_*`).

Блок для вставки:
```text
#ПРИМЕРЫ СТИЛЯ (только тон и форма; содержание и формулировки НЕ переносить)
Тип: {{programType}}
Пример формулировки цели: «{{styleExamples.goal}}»
Пример результатов: «{{styleExamples.outcomes}}»   // напр. «Формулировать продуктовую гипотезу и обосновывать выбор метрик.»
Пример строки учебно-тематического плана: «{{styleExamples.topicRow}}»
Правило: перефразируй в своей предметной области; не используй ни одной фразы длиннее 6 слов из примеров.
```
Фрагменты хранятся в `prompts/style/{doop,dpp}.json`, отбираются кодом по `programType`.

## 5. RAG: справочник ПС, нормативных актов и референсов (`skeleton`, `sources`, `content`)

**Зачем.** Главный стоп-критерий кейса — выдуманные ПС, приказы, источники. Модель выбирает только из справочника по ID; всё прочее — `verified:false` с пометкой. Справочник (`registry/*.json`, собирает PM) — проверенные людьми ПС с кодами ТФ, 273-ФЗ, приказы, литература, документация. Ретривер: фильтр по `programType` + поиск по `request.params.domain` (BM25/эмбеддинги), top-k = 10–20 записей.

```text
#РОЛЬ
Ты — библиограф-методист АЦР.

#КОНТЕКСТ
Ниже ПРОВЕРЕННЫЙ справочник. Ссылаться можно только на его записи по id. Внешние источники вне справочника допускаются только как предложения с пометкой непроверенности.

#ВХОДНЫЕ ДАННЫЕ
Тип программы: {{programType}}; направление: {{request.params.domain}}
Компетенции: {{competencies|json}}
Темы: {{curriculum.modules[*].topics[*].title}}
Справочник нормативных актов: {{registry.normative|json}}   // [{registryId,citation,url,year}]
Справочник профстандартов: {{registry.profStandards|json}}  // [{registryId,standardCode,standardTitle,approvalOrder,laborFunctions:[{code,title}]}]
Справочник литературы и ресурсов: {{registry.literature|json}}
Выдержки из референсов (для содержания, не для копирования): {{referenceChunks|json}}

#ЗАДАЧА
1. Подбери нормативные акты (для DPP_PK обязательно 273-ФЗ и ПС из привязок компетенций).
2. Подбери 3–5 основных, 3–5 дополнительных источников, 3–7 интернет-ресурсов и ПО, относящихся к темам.
3. Если нужного источника нет в справочнике, можешь предложить его в "proposed" — он попадёт в программу с пометкой «не подтверждено».

#ОГРАНИЧЕНИЯ
- Не придумывай номера приказов, коды ПС/ТФ, ISBN, годы, URL. Если не уверен в атрибуте — null.
- DOOP_GENERAL: профстандарты не указывать.
- Не цитируй выдержки референсов дословно.

#ФОРМАТ ОТВЕТА
{"fromRegistry":[{"registryId":string,"category":"normative|main|additional|internet|software","topicIds":[string]}],
 "proposed":[{"category":"main|additional|internet|software","citation":string,"url":string|null,"year":int|null,"topicIds":[string]}]}
```
Код: `fromRegistry` → `sources[]` c `verified:true`, `verification.method:"registry"`; `proposed` → `verified:false`, `unverifiedMark:"[не подтверждено]"` (до техники 6). Неизвестный `registryId` → отброшен + `validationReport.checks` warning.

## 6. Факт-чек источников с уровнем уверенности (`sources`)

**Зачем.** Уменьшает число «не подтверждено» без риска галлюцинаций. Модель даёт только оценку уверенности и что проверить; **финальный `verified` ставит код**: `true` только если источник есть в справочнике, или URL ответил 200 и заголовок страницы совпал, или ISBN найден. `confidence` модели сам по себе не делает источник подтверждённым.

```text
#РОЛЬ
Ты — осторожный фактчекер. Признавать незнание — нормально.

#ВХОДНЫЕ ДАННЫЕ
Источники без подтверждения: {{sources[verified=false]|json}}
Результаты автоматических проверок (HTTP, ISBN, справочник): {{checkResults|json}}

#ЗАДАЧА
Для каждого источника оцени: существует ли он в указанном виде (автор, название, год, издательство, URL), уровень уверенности, какие атрибуты сомнительны, как это проверить.

#ОГРАНИЧЕНИЯ
- confidence: high — уверен, что существует ровно в таком виде; medium — источник существует, но атрибуты могут отличаться; low — не уверен в существовании.
- Не «исправляй» атрибуты по памяти, если confidence не high; предлагай fix только для явных опечаток.
- Если источник, вероятно, выдуман — recommendation:"remove".

#ФОРМАТ ОТВЕТА
{"checks":[{"sourceId":"SRC5","confidence":"high|medium|low","doubtfulFields":["year","url"],"howToVerify":string,
  "recommendation":"keep_unverified|remove|replace_from_registry","fix":{"citation":string|null,"url":string|null,"year":int|null}}]}
```
Код: `remove` + low → удалить; иначе оставить с `verified:false`; заполнить `validationReport.summary.unverifiedSources`.

## 7. Самопроверка и автопочинка по `validationReport` (`validate` → `repair`)

**Зачем.** Отличие от «один промпт → документ»: агент сам находит ошибки (Java-валидатор) и чинит только сломанное. Цикл ≤ 3 итераций, далее ошибки остаются в отчёте для методиста. **Часовые ошибки (`HOURS_*`) LLM не чинит** — их исправляет код повторной раскладкой; LLM получает только содержательные (`COVERAGE_*`, `REFS`, `SECTIONS`, `DELIVERABLES`, `REVIEW_*`, `COPY_*`).

```text
#РОЛЬ
Ты — методист, исправляющий замечания автоматической проверки. Ты меняешь минимум.

#КОНТЕКСТ
Валидатор нашёл ошибки. Исправь ТОЛЬКО указанные фрагменты; всё остальное в программе утверждено и не меняется.

#ВХОДНЫЕ ДАННЫЕ
Ошибки: {{validationReport.checks[passed=false && severity=error && ruleId !~ HOURS_]|json}}   // ruleId, path, message
Затронутые фрагменты (по path): {{fragmentsByPath|json}}   // напр. assessment.tests[0].questions[3], curriculum.modules[1].topics[2]
Справочно (только чтение): результаты {{competencies|json}}, ID тем {{curriculum.modules[*].topics[*].id}}

#ЗАДАЧА
Для каждой ошибки предложи исправление:
- COVERAGE_TOPIC (результат не раскрыт ни в одной теме) → добавь outcomeId в наиболее подходящую тему и дополни её activities[].content;
- COVERAGE_ASSESS (результат проверен <2 раз) → добавь новый вопрос или задание с этим outcomeId;
- REFS → замени несуществующий ID на существующий;
- SECTIONS/DELIVERABLES → дозаполни недостающее поле.

#ОГРАНИЧЕНИЯ
- Не меняй поля hours, id существующих элементов, порядок модулей и тем.
- Не трогай фрагменты, которых нет во входных данных.
- Новые ID — следующие свободные по порядку (передаются: {{nextFreeIds|json}}).

#ФОРМАТ ОТВЕТА
{"patches":[{"ruleId":string,"op":"replace|add","path":string,"value":<фрагмент по $defs схемы>,"comment":string}]}
```
Код применяет патчи (JSON Patch-подобно), запускает валидатор заново, отмечает `checks[].autoFixed=true`, увеличивает `validationReport.iterations`.

## 8. Точечная доработка темы (`repair`, режим edit)

**Зачем.** Методист меняет одну тему без пересборки комплекта. Код строит граф зависимостей по ID: тема → `activities`, `seminarTasks[topicId]`, `questions[topicIds]`, `lectures[topicId]`, `calendar.sessions[topicIds]`. Часы темы не меняются (если методист меняет часы — код перераскладывает их и перепроверяет суммы).

```text
#РОЛЬ
Ты — эксперт-практик, дорабатывающий одну тему по замечанию методиста.

#ВХОДНЫЕ ДАННЫЕ
Замечание методиста: {{editInstruction}}
Тема: {{curriculum.modules[i].topics[j]|json}}
Зависимые элементы: задания {{assessment.seminarTasks[topicId=T]|json}}, вопросы {{assessment.tests[*].questions[topicIds∋T]|json}}, лекция {{lectures[topicId=T]|json}}
Соседние темы (не дублировать): {{siblingTopics|titles}}
Результаты, на которые ссылаются другие темы и оценочные средства (не удалять без замены): {{outcomesUsedElsewhere|ids}}

#ЗАДАЧА
1. Перепиши тему по замечанию.
2. Обнови ТОЛЬКО те зависимые элементы, которые после изменения стали не соответствовать теме; остальные верни в списке unchanged.
3. Если изменились outcomeIds темы — убедись, что каждый удалённый результат всё ещё раскрыт в другой теме (из списка выше), иначе не удаляй его.

#ОГРАНИЧЕНИЯ
- hours темы и id элементов не меняй. Новые элементы — ID из {{nextFreeIds|json}}.
- Заголовок титульного слайда лекции = новый title темы.

#ФОРМАТ ОТВЕТА
{"topic":<объект по $defs/topic>,
 "updated":{"seminarTasks":[<$defs/seminarTask>],"questions":[{"testId":string,"question":<$defs/question>}],"lectures":[<$defs/lecture>]},
 "unchanged":[string],"changeNote":string}
```
Код: применяет, перезапускает валидатор (техника 7 при ошибках), пишет `generation.revisions[] = {at, scope:"T…", note: changeNote}`.

## 9. Итеративное тестирование: LLM-судья по чек-листам тест-кейсов (офлайн)

**Зачем.** Ежедневный прогон 5 открытых кейсов (как у организаторов с 17.10) → регрессия качества промптов. Пункты чек-листа делятся на **кодовые** (часы = N, практика ≥ X, 10 вопросов с outcomeIds, 8 занятий в 4 недели, нет ПС для ДООП, ровно 254 СРС + 2 ИА, пустые реквизиты) — проверяются ассертами в `tests/checklists/*.json` — и **смысловые** (язык понятен школьнику, задания на банковских ситуациях, тема об этике есть) — их оценивает судья. Судья — по возможности другая модель, чем генератор.

```text
#РОЛЬ
Ты — эксперт жюри, проверяющий сгенерированную программу по эталонному чек-листу. Ты строг и опираешься только на текст комплекта.

#ВХОДНЫЕ ДАННЫЕ
Запрос: {{request.rawText}}
Пункты чек-листа для смысловой проверки: {{checklist.semanticItems|json}}   // [{itemId,text}]
Релевантные фрагменты комплекта: {{kitExcerpt|json}}   // header, doop|dpp, competencies, curriculum (titles), finalAttestation, assessment (выборка), lectures (titles), sources
Результаты кодовых проверок (для сведения): {{checklist.codeResults|json}}

#ЗАДАЧА
Для каждого пункта: найди доказательство в комплекте (JSON-путь и короткая цитата), вынеси вердикт и объясни.

#ОГРАНИЧЕНИЯ
- Нет доказательства → fail или partial, не додумывай.
- Цитата ≤ 25 слов, path — реальный путь в комплекте.
- Арифметику часов не оценивай.

#ФОРМАТ ОТВЕТА
{"caseId":string,"results":[{"itemId":string,"verdict":"pass|partial|fail","evidencePath":string|null,"evidenceQuote":string|null,"reason":string,"fixHint":string|null}],
 "score":number}   // доля pass (+0.5 за partial)
```
Результаты сохраняются в `eval/results/<date>/<case>.json`; падение `score` относительно прошлого прогона → разбор промптов. Эти данные пригодятся для слайда «качество» на защите.
